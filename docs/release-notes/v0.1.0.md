# v0.1.0 — release notes

The first release of Scion: a version control server that stores its
history as content-addressed objects in Postgres, cache tiers in front
of it, and `scn`, a client that lands changes from many agents at once
and checks out sparse trees through the tiers.

A reader takes the release two ways: the source at the tag (the
README's quick start builds and runs it), or the release's artifacts —
the four binaries (scion-server, scion-cache, scion-daemon, scn), the
source tarball, and a CycloneDX SBOM per shipped binary's crate, each
with a GitHub artifact attestation and a checksum. Windows is not
supported. The release ships Linux x64 and macOS arm64 binaries;
linux-aarch64 returns with v0.8
([ROADMAP.md](../ROADMAP.md)). The supported platforms are the ones
the matrix names: Ubuntu 24.04 x86-64 and macOS 15 arm64, Postgres 17
on every push and 16 and 18 nightly and on a release candidate's
dispatch ([support.md](../support.md)).

**Postgres 16, 17 or 18 is required.** The metadata store is Postgres
and there is no other: every store command takes the database URL from
`--postgres-url-file` or `SCION_POSTGRES_URL` (`--postgres-url` still
works in v0.1.0 with a warning — it prints the credentials to every
local account through the process list — and is removed in v0.2.0).
A data directory that holds an older, SQLite-era store (a `scion.db`)
is refused: this release keeps metadata only in Postgres and does not
migrate it. A fresh, empty data directory opens and takes its marker.

## What is proven

Every claim below is a gate that ran on the released commit; the check
names where to look.

- The whole CI suite: build, clippy (three runs: the workspace's
  all targets, the writable-mount feature build, and the release
  build's lib+bins shape, which keeps the test-hooks feature off),
  fmt, rustdoc, cargo-deny (advisories), the unit and integration
  suites on Linux, the same on macOS, the Postgres cells natively
  (17 per push, 16 and 18 nightly and on a release candidate's
  dispatch), the power-loss drill (LazyFS fault injection), an NFS
  mount run, gRPC conformance from a non-Rust client, a fuzz smoke,
  the MSRV build, the Docker demo, and the scorecard policy.
- The README's quick start walks end to end on every supported
  platform, from a clean build, once under umask 022 and once under
  002, in the release-smoke job — against Postgres, the release's
  only backend.
- A restore of a stated store passes `fsck` and serves
  (crates/scion-server/tests/backup.rs); the durability point is
  documented in [operations.md](../operations.md) §3.
- Secrets (bearer tokens, TLS keys, ticket keys) are read through one
  checked descriptor: ancestor directories, symlink refusal, owner, and
  mode on the open file; POSIX ACLs on top. The release notes of the
  security section of the changelog carry the details.
- The release artifacts are built twice, from the signed tag, on
  separate runners, and the two builds agree byte for byte before
  anything is published; each artifact carries an attestation the
  reader verifies with
  `gh attestation verify <file> --repo bnsd55/openscion`
  ([slsa.md](../slsa.md)).

The 72-hour soak (Run A) ran 66 h 40 min on `5f0e428f` and was accepted
as a partial run ([#399](https://github.com/bnsd55/openscion/issues/399));
it predates the backend switch and is not evidence for this tag.

## Measured numbers

With the runs they came from; the scripts that make them are in
`scripts/` and the method is in [benchmarks.md](../benchmarks.md).

### Sparse checkout, 50 jobs at once

From one `bench.yml` run
([run 39306408455](https://github.com/bnsd55/openscion/actions/runs/39306408455),
`main` at `7b7789f`, `ubuntu-24.04`, tokio at `tokio-1.53.0`, 5
repetitions per state, medians):

- A cold checkout of `tokio/src/` (377 files, 3.3 MiB) through a fresh
  daemon: 1.50 s wall, 0.09 server CPU s, 0.91 MiB sent.
- git clone of the same files: 33.15 s wall, 799.89 MiB of pack —
  22.1x slower, 879x more bytes.
- git clone --filter=blob:none: 13.96 s — 9.3x slower.
- The warm daemon: 1.35 s; git's mirror clone 0.80 s — the one place
  git is faster (1.7x), on local object reuse where nothing moves over
  the wire.

The full tables, with CPU and bytes and what the numbers do not
measure, are in [benchmarks.md](../benchmarks.md).

### Restore

From the `restore-bench` workflow
([run PENDING — restore-bench dispatched at the release commit],
the stated store: 20 repos, 1000 changesets, about 32 MiB of raw blob
content in files of about 32 KiB, on the fixed `ubuntu-24.04` runner):

- restore 0.0 s (build 0.5 s), against the 600 s bound the workflow
  enforces. The store is small; the number is the drill's, not a
  promise, and the workflow reprints it on every run.

### Capacity envelope

Measured and published
([run 40864498937](https://github.com/bnsd55/openscion/actions/runs/40864498937),
`main` at `f4d62b59`,
[operations.md §7](../operations.md)): one named machine (the fixed
`ubuntu-24.04` runner, 4 vCPU, 16 GiB RAM, ext4), the benchmark's tokio
dataset, Postgres 17.11 behind the server, two to two hundred writers,
zero to twenty readers. Every number below is a cell of that run's
table, named by its writers and readers. A land's p99 stays under
250 ms while readers do not contend (2-writer cells: 57.8 ms with no
readers, 245.3 ms with 20), and lands run 23.2 to 8.2 a second across
the grid's left edge. The cells that cross the section's own 5-second
edge: 50 writers with 20 readers (land p99 7,708.9 ms) and every
200-writer cell (8,081.3, 16,945.7 and 29,120.7 ms). Checkouts stay
fast everywhere: a p99 of 288-1,063 ms. Zero timeouts and zero errors
in every cell of the published table. The growth columns: the blob
store takes 5,668-5,674 KiB per 1,000 lands, the database adds
34,494-87,506 KiB. The full table, and how a cell defines its edge,
are in operations.md §7.

## What this release does not have

- No crates.io publish: the crates carry the metadata for a later
  publish, decided against until a real outside consumer exists.
- No failover, no multi-server story: one server per store
  ([ROADMAP.md](../ROADMAP.md)).
- The mount every build has is read-only: the writable overlay is a
  build feature kept out of release builds until a rewrite that opens
  each path step by handle passes the hostile tests.
- The compat window, the N-1 support split, and the second operator
  drill are v0.4 and v0.8 gates, not this release's. The two N-1
  drills the project ran while the store carried both backends (the
  tagged-store ladder and the N-1 restore drill) return with the
  first release tag, when a release pair exists to prove.
- `--postgres-url` is removed in v0.2.0: a URL on the command line
  shows in the process list. Pass the URL through
  `--postgres-url-file` or `SCION_POSTGRES_URL`; a script that still
  hands the URL on the command line gets a warning until then.

## Upgrading

Nothing to upgrade from: the first release. The schema the release
writes — the Postgres schema — is documented in
[stability.md](../stability.md); a patch release of v0.1.x may change
it only as that document allows.
